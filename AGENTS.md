# wishlist

Shared wish lists with reservations the owner never sees.

The global baseline already applies here and is not repeated below.

## Layout

- `cmd/wishlist` wires the service: config, construction and shutdown. `embed.go` embeds
  `dist/` (the built SPA, written by `task web:build`). It sits under `cmd/` rather than
  `internal/` because `go:embed` resolves relative to the file holding the directive.
- `internal/config` loads and validates the service's own environment once, aggregated into
  one error. Every secret-shaped variable has a `_FILE` twin (`DB_PASSWORD` or
  `DB_PASSWORD_FILE`).
- `internal/store` is the whole database access: a pgx pool, the embedded migrations in
  `migrations/` applied at startup, `owner.go` (`OwnerStore`) and `guest.go` (`GuestStore`).
  See "The store boundary".
- `internal/dbtest` gives a test its own database on a real PostgreSQL, see "Store tests".
- `internal/webapp` builds the public handler (govue's middleware chain, the SPA).
  `internal/webapp/owner` is the owner API, `owner/dto` its request and response types,
  `owner/ownertest` an in memory store for handler tests. See "The owner API".
- `internal/depsync` checks that `go.mod` and `web/package.json` pin the same govue version,
  and that `web/pnpm-lock.yaml` still resolves govue's Vue package to its `/web`
  subdirectory; see "govue's two halves move together" below.
- `web/` is the Vue SPA, consuming govue's Vue package as a pnpm git dependency.
  `web/src/theme/wishlist.css` fills govue's design token contract. It is generated from
  the two seed colours in `web/src/theme/seeds.json` with govue's `generate-theme` script
  (`node <govue>/web/scripts/generate-theme.ts --config src/theme/seeds.json --out
  src/theme/wishlist.css`, Node 24 or later). Change a seed, regenerate, never edit the CSS
  by hand. `web/src/theme/contrast.test.ts` checks it against WCAG 2.2 AA.
- `charts/wishlist/` is the Helm chart for this one workload. `docker-compose.yaml` is a
  local development stack.

## A build needs the frontend first

`cmd/wishlist` cannot compile against an empty `dist/`, because `go:embed` fails when its
pattern matches no file at all. `dist/` is gitignored, generated by `task web:build`.

`task build` and `task test:go` both declare that dependency, so running either one through
Task always populates the frontend first. A bare `go build ./cmd/wishlist` or
`go test ./cmd/wishlist/...` outside Task fails on a fresh checkout for that reason; run
`task build` or `task test:go` instead, or `task web:build` once by hand before reaching for
the Go toolchain directly.

## govue's two halves move together

govue releases a Go module and a Vue package under one tag. `go.mod`'s
`require github.com/ostendorf-cloud/govue` and `web/package.json`'s `@ostendorf-cloud/govue`
pnpm git dependency must always name the same tag: a mismatch means this repository takes
half of a govue release and not the other half, silently. `task check:govue-version`
(`internal/depsync`) enforces this, the same way `ostendorf.tech` does.

## The store boundary

The store has two sides that share only the pool. `Core` owns `Open`, `Close`, `Ping` and
`Migrate`, and hands out `OwnerStore` (`Owners()`, all methods in `owner.go`) and
`GuestStore` (`Guests()`, all methods in `guest.go`). Only `guest.go` may name the
`reservations` table, and the comments the guests write are there too. A handler for the
owner must be given an `OwnerStore` and nothing else: only then does the compiler stop it
from calling a guest method. That is true once the wiring passes an `OwnerStore`. The handler
layer half is `internal/webapp/owner/boundary_test.go`, see "The owner API".
`boundary_test.go` needs no database and runs everywhere. Read it for what
it is: a guard against accidents by a contributor, not against a determined one. The real
defence is the handler layer review and the code review. It checks:

- every constant string of the other `.go` files, evaluated with `go/types`: literals, named
  constants, constants from another file or from `guest.go`, constant `+` expressions of
  them however far apart the parts are, and package level string variables initialised with
  such an expression, also from `guest.go`. Case insensitive, escapes decoded.
- the `U&"` identifier spelling, catalog queries (`pg_stat`, `pg_class`, `pg_catalog`,
  `information_schema` and a few more) and SQL that builds SQL (`query_to_xml`,
  `cursor_to_xml`, `ts_stat`, `xpath_table`, `dblink`, `execute`, `do $` and a few more) in
  those strings.
- imports: the other files may import only the standard library, pgx and `internal/config`,
  never `"C"`, because the constants of any other package cannot be evaluated and a cgo
  preamble is C source.
- files are attributed by their real name: a `//line guest.go:1` directive does not exempt
  a file.
- every other file in the store tree, of any extension and any case, outside `migrations/`,
  and every `_test.go` file a `go:embed` names.
- `migrations/`: only `NNNN_name.sql` files, with no catalog query and no dynamic SQL. The
  statements are cut and the comments removed by a reader that knows single, `E`, double and
  dollar quoted text, so `--` or `/*` inside a string hides nothing. A
  statement that mentions the table has to be its own `create table`, an index on it or an
  `alter table` of it that does not rename it, move its schema, inherit or attach a
  partition. A view, function, rule, trigger or another table's foreign key over it fails.
  The current migration needs none of the forbidden constructs, and a later one that does
  has to change the test in review.
- that each side's methods stay in their own file, the two types share no method, and no
  file other than `store.go` mentions the other side's type, `Guests`/`Owners` or a guest
  method. `guest.go` declares no package level function, only methods of `GuestStore`.

What it does not catch:

- a name built when the program runs: `fmt.Sprintf`, `strings.ReplaceAll`, a rune slice,
  a function result, a package level variable initialised by a call, a struct tag read
  through `reflect`.
- a name built from local variables (`x := "reserv"; x + "ations"`, `x += "ations"` in a
  function, a package variable `+=` in `init()`): only package level declarations are
  evaluated.
- a name split inside an embedded template or a `.s` file, and a quoted `go:embed` pattern
  that contains a space.
- a constant of an allowed package changed to spell the name.
- a way to find the table through the database that the marker lists do not name:
  `alter table reservations set (...)`, `owner to`, `create publication ... for all tables`,
  `pg_sequences` (which leaks only the global reservation count).
- the gaps of the side check: an unexported guest method, a type alias for `GuestStore`
  declared in `store.go`, a call by reflection on the method name.
- whether a migration object that does not mention the table is harmless.

No static test can close those. The handler layer review and the code review cover them.
A new store file that needs reservations is a design change, not a test change: see
`docs/adr/0001-blind-reservations.md`.

Each migration runs in one transaction with its bookkeeping row, so `create index
concurrently` cannot be a migration. Extend the runner first. The password from `DB_PASSWORD`
or `DB_PASSWORD_FILE` is whitespace trimmed by govue's `envconf`, from the variable and from
the file alike.

## The owner API

Endpoints under `/api/v1/owner`, in `internal/webapp/owner`. Lists and wishes: create, read,
edit, archive, delete, order a wish up or down, move a wish to another list. The route table
(`Routes()`) is the list of endpoints. Ids are in the path, JSON bodies are strict (unknown
fields, a second value and a missing or wrong content type are refused, 64 KiB at most), field
errors come as stable keys (`required`, `too_long`, `invalid`) in `error.details`, never as text.

### Blindness of the responses (ADR 0001, response layer)

Mechanism: reflection over the response types. Every handler returns a typed value and one
adapter in `owner.go` writes it, so the route table names the type of every response that
route sends. That holds for the routes in `Routes()` only. Two tests keep it true:
`TestOnlyTheAdapterWritesAResponse` fails when any file under `internal/webapp` writes a body
outside the adapter, and `TestEveryRegisteredPatternComesFromTheRouteTable` fails when a
handler is registered anywhere except from the table (and the two catch alls in `webapp.go`).
Error bodies are govue's envelope, which the walk does not see: `fieldProblem` in `validate.go`
is the only place that sets details, and it fails closed unless every key is a known request
field and every value one of the three codes.
`blindness_test.go` walks each response type: struct fields (embedded too), pointers, slices,
arrays and maps. It fails on any named type of `internal/store` (which covers `Reservation`,
`GuestWish`, `GuestList` and whatever is added to `guest.go` later), on a type or field whose Go
or JSON name matches `reserv|guest|taken|bought|pledge|claim|purchas|book|contrib|donor|amount_?cents`
(a heuristic: the typed walk is the real guard), on an interface (an `any` field is a
violation), a func or a channel, on a `[]byte` or `map[string]string` field, and on a type with
its own JSON or text encoding, which would hide its fields.
`TestTheWalkCatchesEveryWayAReservationCanGetOut` proves each shape fails.
Why reflection and not a generator or a lint rule: it follows the types the encoder really
serialises, it needs no extra tool in `mise.toml`, and it fails in `go test` on every machine.

- The one allowed name is `dto.List.ReserveOpen`: the owner's own switch for closing a list,
  a setting and not data about what was taken. `allowedNames` in the test lists it; keep that
  list short and reviewed.
- Response types are explicit copies in `owner/dto`. A store struct is never sent as it is,
  and `owner/dto` must not import the store.
- `TestOnlyTheAdapterWritesAResponse` keeps handlers from writing around the adapter.
- `TestNothingUnderWebappReachesTheGuestSide` is the handler layer rule of the store boundary:
  code under `internal/webapp` may name only `OwnerStore`, `ErrNotFound`, `List`, `Wish`,
  `ListInput` and `WishInput` of the store, and never `Guests`, `Owners`, `Core` or
  `GuestStore`. It reads names, so it does not catch reflection or generated code.

### Who the owner is

`owner.Resolver` (`func(r *http.Request) (ownerID int64, ok bool)`) is the only source of the
owner id. The id is an `int64`, like the store's. Handlers answer 401 when it is not ok and
never read an owner id from the body, the query or the path.

The owner's sign in is issue 4 and waits for a govue release. Until then
`cmd/wishlist/resolver.go` (`resolveOwner`) returns a resolver that always answers not ok, so
every owner endpoint answers 401. Issue 4 plugs in at two places, both in `cmd/wishlist`:

1. `resolveOwner` returns a resolver that reads govue's session and maps it to an owner id
   (`UpsertOwner` by subject).
2. `buildHandler` in `main.go` passes the matching `csrf.Expected` as
   `webapp.Config.CSRFExpected` (`csrf.Token(key, session.ID)`), and the page renders the token
   into `<meta name="csrf-token">`, which `web/src/api/owner.ts` already reads. Until then only
   the protector's origin check applies (Sec-Fetch-Site and Origin), which refuses cross site
   writes.

Development owner: with `WISHLIST_DEV_OWNER=<name>` the resolver signs every request in as one
account, created on first use. `config.Load` refuses it unless `ADDR` is a loopback address, or
`WISHLIST_DEV_OWNER_ANY_LISTENER=true` says the port is reachable on loopback by other means.
`docker-compose.yaml` sets both: the container listens on every interface and the port is
published on `127.0.0.1` only. The Helm chart passes neither and has no free form `env`, so a
deployment cannot turn it on by accident. Remove the development owner when issue 4 lands, or
keep it for compose only. To try the SPA: `docker compose up --build`, open
`http://127.0.0.1:8080`.

### Refusals

A row of somebody else, a row that does not exist and a malformed id are one answer: 404 with
the fixed body of `refusal` in `handlers.go`. A bad body is refused before the store is asked,
so the answer to it does not depend on whether the row exists. The store scopes every query by
owner id and returns `ErrNotFound` for a foreign row; `fail` maps only that to the refusal.
Moving a wish to a list needs both rows to be the owner's.

The public listener serves built files, and `index.html` only for GET and HEAD of the SPA's
own routes (`spaRoutes` in `webapp.go`, kept in step with `web/src/router.ts` by a test).
Everything else is a 404: JSON under `/api/`, plain text elsewhere. `/metrics`, `/healthz` and
`/readyz` are on the admin listener only, and `scripts/smoke-test-image.sh` pins that. A new
top level route in the SPA needs its first segment in `spaRoutes`.

The rate limiter keys by connection address. Behind an ingress everyone shares one bucket, so
it needs a trusted proxy setting before the first deployment.

Left out on purpose: images (the keys that delete returns are counted in a debug log line, the
objects are not deleted: image milestone), share tokens, guest access, translations, link
import. Security headers (CSP) are not set by this handler yet; they need a check against the
built bundle in a browser.

## Store tests

The tests against a real PostgreSQL (`internal/store/db_test.go`,
`cmd/wishlist/database_test.go`) read the server's URL from `WISHLIST_TEST_DATABASE_URL`, for
example `postgres://wishlist:dev-password-not-real@127.0.0.1:5432/postgres?sslmode=disable`.
The role needs `CREATEDB`: each test creates and drops a database of its own.

```sh
docker compose up -d postgres
export WISHLIST_TEST_DATABASE_URL='postgres://wishlist:dev-password-not-real@127.0.0.1:5432/postgres?sslmode=disable'
task test:go
```

Without the variable those tests skip with a message naming it, and `task test:go` prints a
warning before it runs. With `CI` set they fail instead of skipping. The `test` job in
`.github/workflows/checks.yaml` provides a PostgreSQL service container and the variable.
There is no fake database: a fake is used only for the client's error paths, by pointing
the real client at a closed port.

## Scope of this milestone

This repository rewrites the existing `old_wishlist` service, a Go application with
server-rendered templates, into a Go API with a Vue SPA on govue, so it looks and behaves
like the other `ostendorf-cloud` applications. This milestone is the scaffold alone: the
embedded SPA shell and the Go entry point serving it, with health, readiness and metrics on
govue's admin listener, plus the PostgreSQL schema and its store, and the owner's API and SPA
on top of it. Left out, tracked as later milestones:

- owner login through OIDC (issue 4; the owner API takes its owner from a resolver, see "The
  owner API")
- images, kept in an object store
- the HTTP API for share tokens, reserving and comments
- two languages
- link previews when a wish is imported from a product link

A reservation is blind: the owner can never learn what was taken. That is a property of the
queries themselves, not of an authorization check, and it stays honest only because it has
its own test proving it, the way `old_wishlist`'s own blind test did. Importing a wish from a
link is also planned to improve on the rewrite: a product link from a large shop should yield
a usable title, picture and price, which `old_wishlist` did not do.

Neither OIDC nor an object store client exists in this repository yet.
